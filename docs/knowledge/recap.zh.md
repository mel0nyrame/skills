# Recap 怎样把会话变成以后能读懂和查到的知识

[English](recap.md) | 简体中文 · [全部指南](../README.zh.md)

`recap` 会把指定会话整理成专题文档，保留解释、理由、操作过程和来源。它还可以查询已有专题，或维护指定知识。适合保存那些以后还需要重新理解的内容，例如排障过程、工程决策理由和可重复执行的方法。

一次长会话可能讨论了两个独立问题，后来又纠正了其中一条结论。整理后，读者应能分别理解这两个主题，知道哪条结论被修正，以及哪些来源支持当前说法。只保存一个聊天日期或几句结论，达不到这项工作的目标。

下面的文件说明来自[执行指令](../../skills/knowledge/recap/SKILL.md)、[文档格式](../../skills/knowledge/recap/references/formats.md)和[辅助脚本](../../skills/knowledge/recap/scripts/knowledge.py)。本页介绍现有流程，不会替你初始化知识库。

## 先决定知识保存到哪里

知识库位置按显式指定的根目录、`RECAP_KNOWLEDGE_ROOT` 环境变量、`~/.agents/knowledge` 默认目录的顺序决定。它是独立的知识目录，不应因为你正在修改某个项目，就默认把资料写进该项目。

脚本需要 Python 3 和 Git。全文检索通常使用 Python 自带 SQLite 的 FTS5 功能；不可用时，可以明确采用文本检索降级。助手访问知识库前先读取该目录自己的 `AGENTS.md`。

**初始化会建立 Git 仓库并创建首次提交。** 后续候选检查和正式发布也可能创建提交。如果你要求全程不创建 Git 提交，就先要求输出未提交草稿，避免启动这些流程。

## 怎样提出一次保存请求

下面是请求示例。把目录换成你决定使用的位置。

```text
$skills:recap
把这段会话里的排障方法和决策理由整理成专题知识。
知识库使用 /path/to/my-knowledge，先核对该目录及其已有规则。
保留问题背景、判断依据、失败尝试、适用条件和来源位置。
先给出准备新增或更新的主题及实际写入位置，等我确认后再运行会创建 Git 提交的步骤。
不要修改当前项目的 Git 状态。
```

示例使用本项目的 Codex 插件。单独安装时用 `$recap`，Claude Code 中用 `/skills:recap`。它只由用户显式调用，普通对话不会自动触发保存。

## 保存过程中会发生什么

助手先确认选中的会话、分支和读取范围，查找已有相关主题。已有主题能够容纳新发现时，就在原有解释上更新，避免为每次聊天生成一份近似副本。会话中的推测、已执行测试和用户纠正应当分开处理。

随后准备专题正文和必要来源记录。来源要说明实际读过的范围，未读附件或缺失历史也要保留。来源链接可以帮助追溯，但原始会话以后被删除时，只能独立核查已经保留下来的必要摘录，不能保证完整重放聊天。

正式保存走候选工作区和检查流程。并发修改同一篇内容时，还需要独立审查。最后发布对应的内容版本，重新打开文档检查可读性和重要检索，再清理本次成功操作的临时工作区。失败或待审查的工作应保留。

## 具体会生成什么

下面展示经过初始化、保存和检索后可能出现的目录。文件名为示意，实际主题名应描述读者的问题，通常采用用户语言。

```text
my-knowledge/
├── AGENTS.md
├── index.md
├── CHANGELOG.md
├── topics/
│   └── 一个具体专题.md
├── sources/
│   └── host-session-id.md
├── drafts/
├── .git/
├── .state/
│   ├── library.json
│   ├── index.sqlite
│   ├── cursors/
│   └── published/
└── .worktree/
```

| 位置 | 内容和出现条件 |
| --- | --- |
| `topics/**/*.md` | 正式专题正文，包含解释、示例、适用范围和来源链接 |
| `sources/<host>-<session-id>.md` | 会话来源、读取范围、缺口和支持结论的必要摘录 |
| `index.md` | 从主题摘要生成的阅读入口，保留非管理区的已有正文 |
| `CHANGELOG.md` | 本次知识新增或修正了什么、为什么改 |
| `drafts/` | 尚未正式发布的材料，例如来源覆盖仍有缺口的草稿 |
| `.state/library.json` | 知识库格式和分支等机器状态 |
| `.state/index.sqlite` | FTS5 检索时生成或更新的缓存，不是正式知识正文 |
| `.state/cursors/` | 需要追踪增量会话范围时保存的检查点，必须与代表的知识同步 |
| `.state/published/` | 发布操作记录 |
| `.worktree/` | 候选工作区，成功清理后不必持续保留本次操作目录 |

初始化还会建立 `.gitignore` 和内部目录，例如 `.history/`。这些辅助位置不需要人工填满。机器状态、候选目录和检索缓存，也不能替代 `topics/` 里的可读正文。

## 一篇专题打开以后应当是什么样

如果整理的是本集合的打包讨论，正文可以从下面这个片段开始。它是教学示例，不是已经写入知识库的文件。正式文档的元数据由实际保存流程生成。

```markdown
# 外部 Skill 的子模块检出规则

本文说明本集合为什么默认不检出外部 PR 和 Context7 仓库。
适用范围是当前九个内置 Skill 共用分类目录的打包结构。

## 约定及原因
两个外部引用使用 Git 子模块，并在 .gitmodules 中设置 update = none。
上游完整仓库包含其他 Skill，检出后可能改变递归扫描结果。

## 怎样核对
确认两个引用仍是 gitlink，正常初始化会跳过内容检出。
再检查安装器发现的内置 Skill 是否仍为九个。

## 来源
见[会话记录](../sources/host-session-id.md)，保留实际消息范围和必要摘录。
```

这样的正文要让下一位读者理解原因，也知道什么时候需要重新检查。只有“子模块不用初始化”一句话，会丢掉适用条件和验证方式。

## 保存完以后怎样使用

以后可以要求查询一个具体问题。默认检索范围是正式专题，草稿和原始来源不会混进普通结果。

```text
$skills:recap
查询知识库里关于导出权限检查的专题。
解释它为什么需要放在统一服务入口，并给出对应文件和来源。
这次不新增或修改正式知识。
```

查询可能更新检索缓存和锁文件，因此“只查询”不等于磁盘上绝对零写入。如果你需要严格的只读访问，应先说明这一限制，让助手核对访问方式。

检索分别处理标题、别名、摘要和正文。日期、状态和来源路径等元数据不会产生匹配。已定义的参考式链接键名也不参与检索，显示给读者的标签仍可检索。查询 `session.prompt`、`foo_bar`、`std::vector` 时保留完整标识符；也可以单独查询其组成部分。查询 `session.prompt` 时，只提到 `session.stop` 和 `client.prompt` 的页面不会命中。

结果包含正文片段和原文件行号。片段根据归一化后的词元匹配定位，也支持跨标点或跨行的短语。词元是索引处理文字的基本单位。只命中别名时，片段可能显示正文开头，因此仍需阅读专题后再下结论。检索仍依赖字面用词，应提取短关键词，并尝试其他说法。例如，可以要求“查找 `session.prompt`，解释它的完成行为”，或“搜索 `并发 写入`，解释为什么需要锁”。匹配规则和缓存说明见[检索约定](../../skills/knowledge/recap/references/search.md)。已有检索缓存会自动重建，不会修改正式专题或其 Git 历史。

要先确认工具和目录能力，可以在本集合根目录运行下面的检查。替换 `/path/to/my-knowledge`，这个命令本身不创建知识库。

```sh
python3 -B skills/knowledge/recap/scripts/knowledge.py --root /path/to/my-knowledge doctor
```

已有内容的目录不能直接当作空库初始化，需要先检查迁移方案。相关步骤见[发布、迁移和恢复](../../skills/knowledge/recap/references/operations.md)。

## 怎样判断这次知识值得保留

单独打开一篇 `topics/` 文档，读者应能知道它解释哪个问题、在什么条件下适用，以及结论从哪里来。再用另一种说法检索同一问题，检查是否能找到它。

看见发布提交、索引条目或“保存成功”还不够。正文如果只剩几句摘要，理由和操作条件没有留下，就仍然需要重写。默认库位于本机，也不等于已经有异地备份。
