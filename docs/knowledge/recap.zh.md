# Recap 怎样把会话变成以后能读懂和查到的知识

[English](recap.md) | 简体中文 · [全部指南](../README.zh.md)

`recap` 会把指定会话整理成专题文档，保留解释、理由、操作过程和来源。它还可以查询已有专题，维护指定知识、按语境定义的术语表，以及有证据支持的知识画像。适合保存那些以后还需要重新理解的内容，例如排障过程、工程决策理由和可重复执行的方法。

一次长会话可能讨论了两个独立问题，后来又纠正了其中一条结论。整理后，读者应能分别理解这两个主题，知道哪条结论被修正，以及哪些来源支持当前说法。只保存一个聊天日期或几句结论，达不到这项工作的目标。

下面的文件说明来自[执行指令](../../skills/knowledge/recap/SKILL.md)、[文档格式](../../skills/knowledge/recap/references/formats.md)和[辅助脚本](../../skills/knowledge/recap/scripts/knowledge.py)。本页介绍现有流程，不会替你初始化知识库。

入口按任务读取[捕获](../../skills/knowledge/recap/references/capture.md)、[查询](../../skills/knowledge/recap/references/query.md)或维护规则。各文件用带条件的指针连接所需资料，当前任务无需读取无关分支的指令。

## 先决定知识保存到哪里

知识库位置按显式指定的根目录、`RECAP_KNOWLEDGE_ROOT` 环境变量、`~/.agents/knowledge` 默认目录的顺序决定。它是独立的知识目录，不应因为你正在修改某个项目，就默认把资料写进该项目。

脚本需要 Python 3 和 Git。全文检索通常使用 Python 自带 SQLite 的 FTS5 功能；不可用时，可以明确采用文本检索降级。助手访问知识库前先读取该目录自己的 `AGENTS.md`。

**初始化会建立 Git 仓库并创建首次提交。** 后续候选检查和正式发布也可能创建提交。如果你要求全程不创建 Git 提交，就先要求输出未提交草稿，避免启动这些流程。

## 怎样提出一次保存请求

下面是请求示例。把目录换成你决定使用的位置。

```text
$skills:recap
把这段会话里的排障方法和决策理由整理成专题知识。
知识库使用 /path/to/my-knowledge，先核对该目录及其已有规则。
保留问题背景、判断依据、失败尝试、适用条件和来源位置。
先给出准备新增或更新的主题及实际写入位置，等我确认后再运行会创建 Git 提交的步骤。
不要修改当前项目的 Git 状态。
```

示例使用本项目的 Codex 插件。单独安装时用 `$recap`，Claude Code 中用 `/skills:recap`。它只由用户显式调用，普通对话不会自动触发保存。

## 保存过程中会发生什么

助手先确认选中的会话、分支和读取范围，查找已有相关主题。已有主题能够容纳新发现时，就在原有解释上更新，避免为每次聊天生成一份近似副本。会话中的推测、已执行测试和用户纠正应当分开处理。

随后准备专题正文和必要来源记录。来源要说明实际读过的范围，未读附件或缺失历史也要保留。来源链接可以帮助追溯，但原始会话以后被删除时，只能独立核查已经保留下来的必要摘录，不能保证完整重放聊天。

正式保存走候选工作区和检查流程。并发修改同一篇内容时，还需要独立审查。最后发布对应的内容版本，重新打开文档检查可读性和重要检索，再清理本次成功操作的临时工作区。失败或待审查的工作应保留。

## 具体会生成什么

下面展示经过初始化、保存和检索后可能出现的目录。文件名为示意，实际主题名应描述读者的问题，通常采用用户语言。

```text
my-knowledge/
├── AGENTS.md
├── index.md
├── CHANGELOG.md
├── topics/
│   ├── 一个具体专题.md
│   ├── 用户知识画像.md
│   └── Agent术语表.md
├── sources/
│   └── host-session-id.md
├── drafts/
├── .git/
├── .state/
│   ├── library.json
│   ├── index.sqlite
│   ├── cursors/
│   └── published/
└── .worktree/
```

| 位置 | 内容和出现条件 |
| --- | --- |
| `topics/**/*.md` | 正式专题正文，包含解释、示例、适用范围和来源链接 |
| `topics/用户知识画像.md` | 画像路径示例；有依据的捕获首次创建，各概念条目保存在同一份有来源的专题中 |
| `topics/Agent术语表.md` | 某一语境的术语表路径示例；形成可复用术语时创建 |
| `sources/<host>-<session-id>.md` | 会话来源、读取范围、缺口和支持结论的必要摘录 |
| `index.md` | 自动生成专题清单；导读通过已批准的候选维护；清单后的正文保留原样 |
| `CHANGELOG.md` | 本次知识新增或修正了什么、为什么改 |
| `drafts/` | 尚未正式发布的材料，例如来源覆盖仍有缺口的草稿 |
| `.state/library.json` | 知识库格式和分支等机器状态 |
| `.state/index.sqlite` | FTS5 检索时生成或更新的缓存，不是正式知识正文 |
| `.state/cursors/` | 需要追踪增量会话范围时保存的检查点，必须与代表的知识同步 |
| `.state/published/` | 发布操作记录 |
| `.worktree/` | 候选工作区，成功清理后不必持续保留本次操作目录 |

初始化还会建立 `.gitignore` 和内部目录，例如 `.history/`。这些辅助位置不需要人工填满。机器状态、候选目录和检索缓存，也不能替代 `topics/` 里的可读正文。

## 一篇专题打开以后应当是什么样

如果整理的是本集合的打包讨论，正文可以从下面这个片段开始。它是教学示例，不是已经写入知识库的文件。正式文档的元数据由实际保存流程生成。

```markdown
# 外部 Skill 的子模块检出规则

本文说明本集合为什么默认不检出外部 PR 和 Context7 仓库。
适用范围是当前九个内置 Skill 共用分类目录的打包结构。

## 约定及原因
两个外部引用使用 Git 子模块，并在 .gitmodules 中设置 update = none。
上游完整仓库包含其他 Skill，检出后可能改变递归扫描结果。

## 怎样核对
确认两个引用仍是 gitlink，正常初始化会跳过内容检出。
再检查安装器发现的内置 Skill 是否仍为九个。

## 来源
见[会话记录](../sources/host-session-id.md)，保留实际消息范围和必要摘录。
```

这样的正文要让下一位读者理解原因，也知道什么时候需要重新检查。只有“子模块不用初始化”一句话，会丢掉适用条件和验证方式。

## 怎样维护术语和知识画像

用户显式要求整理会话时，recap 还会检查已经明确的术语，以及能够说明指定用户理解程度的证据。它会更新相关的已有专题。只有存在有依据的条目时，才会新建术语表或画像。普通对话不会在后台更新这些资料。

两种资料都使用现有的 `topics/` 格式和候选发布流程。术语表使用 `concept` 类型和 `glossary` 别名。知识画像使用 `research` 类型和 `knowledge profile` 别名。标题和文件名通常使用用户语言。它们仍是可检索、有来源链接的正式专题，无需新增根目录文件或机器状态字段。

例如，首次有依据的捕获可以在所选知识库根目录下新增 `topics/用户知识画像.md`、`topics/Agent术语表.md` 和 `sources/<host>-<session-id>.md`。发布器会更新 `index.md` 的生成清单，向 `CHANGELOG.md` 追加变更说明，并写入 `.state/published/<operation-id>.json`。增量捕获检查点按需保存。仅初始化知识库时，不会出现画像和术语表。

上述文件名是示例。后续捕获更新用途相同的画像和对应语境的术语表，不会为每段会话重新生成一对文件。助手会报告实际保存路径，并说明哪些文件是新增、哪些是更新。

术语表按主题或项目定义术语。正文可以用简短解释和术语条目的直接链接，替代重复的长篇定义。例如，明确含义和语境后，可以采用 `agent = harness + AI` 作为局部简称，但不能据此认定通用定义成立。组成这个定义的术语也需要解释或链接。每篇专题仍需保留必要背景、理由、示例和操作条件。

知识画像会区分用户的实际表达和助手据此作出的判断。简短条目记录有范围限制的判断，以及支持它的观察和来源消息位置；日期已知时一并保留。记录影响判断的证据条件，仅在有用时补充解释策略。条目可以是一句话，无需固定表单。认识术语、理解机制和能够在场景中应用，是分别记录的维度。

例如，正确列出某个 harness 的工具，可以支持用户认识这些组件的判断。解释工具如何协作，可以进一步支持对机制的理解。知识库里保存了助手的解释，不能证明用户理解了内容。引用内容和用户自述仍需注明证据条件；没有证据的部分保持未知。后续纠正或矛盾观察可以修订同一个条目。

```text
$skills:recap
整理这段会话，并更新相关术语表和知识画像。
以我的表达作为证据，保留消息位置，区分认识组件、理解机制和能够应用。
明确保留尚不确定的判断。
```

用户要求按自己的知识调整解释时，recap 才会查找相关画像证据，再选择解释深度。专题链接的术语定义可以单独读取。普通事实查询无需查找画像，也无需读取画像维护指令。查询只使用已有证据，不新增正式判断。其他助手需要显式查询 recap，或依据已有授权的读取指令使用这些资料。保存专题不会自动改变所有会话。

```text
$skills:recap
解释已保存的 harness 恢复机制专题。
根据相关术语表和画像选择需要介绍的前置知识。
理解程度未知的机制仍需说明。这次查询不要修改正式知识。
```

[存储规则](../../skills/knowledge/recap/references/personalization.md)负责共用的发现与发布约定。定义或引用共用术语时读取[术语规则](../../skills/knowledge/recap/references/glossary.md)。记录理解证据或按用户知识调整解释时读取[画像规则](../../skills/knowledge/recap/references/profile.md)。[相关决策](../agents/adr/0007--recap-knowledge-profile-and-glossary.md)说明为什么复用普通专题。

## 保存完以后怎样使用

以后可以要求查询一个具体问题。默认检索范围是正式专题，草稿和原始来源不会混进普通结果。

```text
$skills:recap
查询知识库里关于导出权限检查的专题。
解释它为什么需要放在统一服务入口，并给出对应文件和来源。
这次不新增或修改正式知识。
```

查询可能更新检索缓存和锁文件，因此“只查询”不等于磁盘上绝对零写入。如果你需要严格的只读访问，应先说明这一限制，让助手核对访问方式。

检索分别处理标题、别名、摘要和正文。日期、状态和来源路径等元数据不会产生匹配。已定义的参考式链接键名也不参与检索，显示给读者的标签仍可检索。查询 `session.prompt`、`foo_bar`、`std::vector` 时保留完整标识符；也可以单独查询其组成部分。查询 `session.prompt` 时，只提到 `session.stop` 和 `client.prompt` 的页面不会命中。

结果包含正文片段和原文件行号。片段根据归一化后的词元匹配定位，也支持跨标点或跨行的短语。词元是索引处理文字的基本单位。只命中别名时，片段可能显示正文开头，因此仍需阅读专题后再下结论。检索仍依赖字面用词，应提取短关键词，并尝试其他说法。例如，可以要求“查找 `session.prompt`，解释它的完成行为”，或“搜索 `并发 写入`，解释为什么需要锁”。匹配规则和缓存说明见[检索约定](../../skills/knowledge/recap/references/search.md)。已有检索缓存会自动重建，不会修改正式专题或其 Git 历史。

要先确认工具和目录能力，可以在本集合根目录运行下面的检查。替换 `/path/to/my-knowledge`，这个命令本身不创建知识库。

```sh
python3 -B skills/knowledge/recap/scripts/knowledge.py --root /path/to/my-knowledge doctor
```

已有内容的目录不能直接当作空库初始化，需要先检查迁移方案。相关步骤见[发布、迁移和恢复](../../skills/knowledge/recap/references/operations.md)。

## 怎样维护导读和查找待处理操作

```text
$skills:recap
列出保留的操作，找出候选工作区缺失的记录。
更新 index.md 的导读，让它覆盖当前专题。
先准备候选并展示差异，再记录我的批准。
保留未发布候选和无关本地文件。
```

`knowledge.py status --all` 列出操作记录、工作区和分支是否存在、是否有发布记录，以及需要恢复的中断事务。旧的 `ready` 操作不能自动视为已放弃。自动清理仍只适用于已成功发布且内容匹配的候选。

某条操作记录损坏时，汇总仍保留其他操作和恢复信息。损坏条目包含错误，汇总标记 `complete: false`。即使命令成功退出，也要检查这个字段。知识库元数据或恢复事务记录损坏时，命令仍会报错。`worktree_exists` 只表示目录存在，不代表 Git 身份有效或候选可以发布。

导读维护只修改生成清单之前的介绍文字。它采用与专题相同的候选、集成和发布流程，并要求用户批准当前候选哈希。两次操作同时修改导读时，需要独立审查。仅生成清单更新不会触发这项要求。维护导读不需要直接修改正式文件。[导读维护决策](../agents/adr/0005--recap-guide-maintenance.md)说明了这项边界的原因。

普通发布可先读[命令清单](../../skills/knowledge/recap/references/checklist.md)。`knowledge.py packet OP --from-dir DIR` 从操作基准版本计算哈希，把明确列出的专题、来源和回执转换为变更包。作者仍需填写修改理由、证据和真实覆盖范围。生成命令不会执行 `inspect` 或发布候选。输入结构见[输入目录格式](../../skills/knowledge/recap/references/formats.md#packet-input-directory)。

生成变更包要求正式库和候选没有未提交修改。候选必须存在、处于编辑状态，并具有匹配的仓库和分支身份。命令在读取声明的文档前报告这些问题，保留外部文件。正式库可以推进到更新的干净版本，哈希仍取自操作基准。单项输入检查不能替代 `inspect` 对整个候选的链接和来源关系验证。

OpenCode 的消息序号表示事件位置，可以从大于 1 的数字开始，也可以跳号。提取器保留原始位置，单独记录数字间隙。完整提取只说明已读取受支持格式的持久化快照，不能证明宿主从未删除或漏存历史。分支、附件、格式或增量前缀确有问题时，仍不能获得完整回执。

对于外部研究目录，`research_index.py /path/to/research` 只向标准输出打印 Markdown 目录。它不写入索引，也不修改知识库。入库状态保持未标记，直到另行核对。正文开头摘录只用于导航。保存目录和添加外部配置指针，需要对应写入授权。覆盖已有批注的索引前，先读[研究资料目录](../../skills/knowledge/recap/references/operations.md#research-inventory)。

## 怎样判断这次知识值得保留

单独打开一篇 `topics/` 文档，读者应能知道它解释哪个问题、在什么条件下适用，以及结论从哪里来。再用另一种说法检索同一问题，检查是否能找到它。

看见发布提交、索引条目或“保存成功”还不够。正文如果只剩几句摘要，理由和操作条件没有留下，就仍然需要重写。默认库位于本机，也不等于已经有异地备份。
