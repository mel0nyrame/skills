# Project Git 怎样隔离并行任务并安全交付

[English](project-git.md) | 简体中文 · [全部指南](../README.zh.md)

`project-git` 建立或遵循仓库的并行工作树偏好，也处理已有改动。它帮助你看懂工作树、拆分合理的提交，并在你明确要求后执行 commit 或 push。

commit 把一个版本保存到本地 Git 历史，push 把提交发送到远程仓库。两步需要分别决定。只想看看代码改得怎样，完全可以只做审查。

## 每个仓库只确认一次工作树偏好

任务开始修改文件或 Git 状态前，助手先读取 `AGENTS.md` 中保存的偏好。没有记录时，询问一次是否为并行任务启用独立工作树。启用和停用都会记录，后续会话直接遵循，不再重复询问。纯只读审查不初始化偏好，也不修改 Git 状态。

启用后，新任务使用独立工作树和分支。当前目录已经是本任务专用工作树时直接复用，包括 Agent 工具预先创建的工作树。默认位置是主工作树根目录的 `.worktree/`。本次任务明确指定的位置或已保存的自定义位置优先。创建项目内的工作树前，助手先核实忽略规则，不猜测各 Agent 的默认目录。

```text
$skills:project-git
为本仓库启用独立工作树，使用默认的 .worktree/ 位置。
把选择写入 AGENTS.md。不要 commit 或 push。
```

旧分支缺少记录时，助手从主工作树的专用偏好小节读取。该步骤只复用工作树偏好，其他指令仍按原有范围适用。初始化时保留其他改动，并报告偏好和忽略规则的写入位置。已有改动保留在原工作树中，迁移需要明确授权。独立工作树不能消除后续合并冲突，也不隔离外部服务。

持久保存、基础分支选择和偏好冲突的处理方式见[工作树流程](../../skills/engineering/project-git/references/WORKTREES.md)。

## 先给清楚操作范围

下面是一个教学示例。工作树中同时有报表导出和登录提示的修改，你只想先检查导出部分。

```text
$skills:project-git
审查报表导出相关改动和测试，指出问题并建议提交分组。
登录提示属于另一项工作，不要碰。
本轮不要修改文件，不要暂存、commit 或 push。
```

这个示例使用本项目的 Codex 插件。单独安装时用 `$project-git`，Claude Code 中用 `/skills:project-git`。助手需要能够运行 Git，并读取适用的仓库规则。

助手应先检查工作树和暂存区，区分本任务改动与其他工作。准备推送时才进一步核对远程地址、目标分支、上游分支和待推送提交。它还要确认验证结果是否真的覆盖当前改动。

## 审查之后怎样提交

你看过分组并决定提交后，可以继续给出明确授权。

```text
只提交报表导出功能和相关测试。保留登录提示的改动。
遵守仓库 hooks，完成后报告提交哈希和剩余工作树。不要 push。
```

助手会按指定路径或部分改动暂存，检查暂存 diff，再执行提交。测试、锁文件和必要生成物应与对应实现保持在一起。一个提交无法用一个意图解释清楚时，才考虑继续拆分，不能仅按文件数量硬拆。

拟定 commit 标题前，助手会检查适用的仓库指令、贡献指南和提交工具配置，分别确认标题格式与说明语言。没有明文要求的部分，再参考近期相关的非合并提交，查找稳定的结构化规范。用户对本次任务的明确要求优先。

| 已有依据 | commit 标题选择 |
| --- | --- |
| 项目要求英文 Conventional Commits，即带类型前缀的提交格式 | `feat(export): add report export` |
| 没有明文要求，但近期提交稳定使用英文 Conventional Commits | 沿用该格式和英文说明 |
| 只有 `fix xxx`、`add xxx`、`修复了xxx`、`加入xxx` 这类零散标题 | 使用默认格式，例如 `feat(export): 增加报表导出` |
| 用户明确要求英文，项目未规定标题格式 | 保留默认结构，使用 `feat(export): add report export` |

格式和语言分别确认，只有未规定的部分才使用默认值。没有稳定规范或明确覆盖要求时，标题采用 `<type>(<scope>): <中文说明>`，其中 scope 可以省略。项目没有分支命名要求时，可以使用 `feat/report-export`。上表是教学示例，不代表已经创建提交。

## 最后得到什么

| 本轮授权 | 主要结果 | Git 状态怎样变化 |
| --- | --- | --- |
| 只读审查 | 问题、建议分组和验证说明，通常留在对话中 | 文件和暂存区保持原状 |
| commit | 一个或多个本地提交及对应哈希 | 指定改动进入 Git 历史，其他工作保留 |
| push | 远程和目标分支的推送结果 | 已授权提交发送到远程 |

默认不会额外生成 `git-report.md`。如果你需要文件形式的审查记录，应说明路径。commit 的主要产物保存在 `.git/` 管理的历史中，不能只靠看到一个 Markdown 文件判断是否成功。

## 怎样确认没有多做事情

审查阶段，查看助手是否把不相关改动当成了本次提交。commit 完成后，核对报告的哈希和提交内容，再看剩余工作树是否保留了其他任务。push 完成后，确认报告的远程和分支就是你要求的目标。

验证失败或 hooks 阻止提交时，应报告原因，保留可恢复状态。不能为了交付绕过 hooks。强推、改写历史和删除远端引用需要与目标范围相匹配的明确授权。

写 PR 正文可以交给外部 [pr](pr.zh.md)。创建或更新托管平台上的 PR 仍是另一项操作。默认命名和记录规则分别见[命名约定](../../skills/engineering/project-git/references/CONVENTIONS.md)、[交付记录](../../skills/engineering/project-git/references/TRACKER.md)和[执行指令](../../skills/engineering/project-git/SKILL.md)。
