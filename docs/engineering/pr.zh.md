# PR 怎样把代码改动写成便于评审的正文

[English](pr.md) | 简体中文 · [全部指南](../README.zh.md)

这是 [Matt Pocock 上游 pr Skill](https://github.com/mattpocock/skills/tree/main/skills/engineering/pr) 的使用说明。它主要编写 pull request 正文，让评审者看懂变化、验证依据和合入风险。GitLab 中对应的请求通常称为 MR。

它直接产出的是文字。上游指令没有要求自动创建一个托管平台请求，也没有要求每次生成固定的本地文件。

## 先准备哪些材料

至少要让助手能够读取这次改动的 diff，并提供或允许它取得实际验证结果。项目已有术语表、PR 模板或贡献要求时，也应说明这些入口。

只有修改后的代码，没有修改前的截图或失败测试时，助手不能补造一段“修改前证据”。它应说明手头证据支持什么，缺少什么。

这个 Skill 需要单独安装，不在本集合的 9 个内置 Skill 中。

```sh
npx skills@latest add mattpocock/skills --skill pr
```

选择 Codex 作为安装目标后，可以使用 `$pr`。通过上游插件安装时，使用上游说明的调用方式。本集合的[子模块](../../skills/engineering/pr)记录的是上游仓库引用，不等于已安装这个 Skill。

## 怎样得到一份可检查的草稿

下面是一个教学示例。保存路径由请求明确指定。

```text
$pr
根据当前 diff 和已有测试结果起草 PR 正文，保存到 PR.md。
摘要要让评审者看懂关键变化，说明证据以及回退和影响范围。
缺少修改前证据时直接写清楚，不要虚构。
本轮只写草稿，不创建或更新平台上的 PR，不 commit 或 push。
```

如果你只想复制正文到平台，把保存那句改成“在对话中返回草稿”。助手不应仅因为调用了 `$pr` 就擅自创建平台请求。

## 正文里应该有些什么

上游模板围绕 `Summary`、`Evidence` 和 `Merge Danger` 三个标题组织变化摘要、证据和合入风险。摘要根据实际问题选择小型目录树、diff 或图，只展示评审需要的关系。文件变化很少时，不必为了套模板画一张大图。

证据应来自真实的测试输出、运行结果或截图。合入风险要说明是否容易回退，以及可能影响哪些使用者或模块。包含删除数据等难以撤销的操作时，不能仅用“风险较低”带过。

例如，你把一个导出函数从页面中移到公共服务，浅层文件树可以说明职责变化。它能帮助评审者定位改动，但不能替代权限测试。这是教学上的组织方式，不代表本集合已经有该导出功能。

## 产物与验收

| 你的请求 | 应有产物 |
| --- | --- |
| 只起草正文 | 对话里的草稿 |
| 明确保存到 `PR.md` | 本地 `PR.md`，完成后应重新打开核对 |
| 明确创建平台 PR | 还需要对应平台工具和授权，成功后才有真实 URL |

检查草稿能否让没参加聊天的人知道改了什么、为什么改、有哪些真实检查，以及还剩什么风险。正文里的文件名应与 diff 对应，链接和测试结果都应能查到。
