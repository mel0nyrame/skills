# Project Engineering 怎样修改项目并留下可用的工程知识

[English](project-engineering.md) | 简体中文 · [全部指南](../README.zh.md)

`project-engineering` 适合让助手进入一个已有项目，完成有边界的实现任务。它会先弄清项目允许怎样修改，找到可复用的实现，确认应该编辑哪个源文件，再执行改动和验证。完成后，后续维护者需要知道的约束也应留在项目里。

这份说明依据[执行指令](../../skills/engineering/project-engineering/SKILL.md)和[工程知识治理规则](../../skills/engineering/project-engineering/references/PROJECT-GOVERNANCE.md)。下面的导出功能仅用作教学示例，路径需要换成你的项目路径。

## 一个任务从哪里开始

假设你要给报表页增加 CSV 导出。只说“增加导出按钮”，助手还不知道是否已有导出服务、哪些字段允许导出，以及页面代码是否由其他文件生成。这些问题会影响改动位置，也会影响验证方式。

你可以在项目中发送下面的请求。示例使用本项目的 Codex 插件。

```text
$skills:project-engineering
给报表页增加 CSV 导出，字段与当前列表一致，保留现有权限检查。
先检查仓库规则和已有导出实现，再决定修改入口。
完成实现和验证，说明改动文件及需要保留的工程知识。
不要暂存、commit 或 push。
```

单独安装时使用 `$project-engineering`。Claude Code 插件中使用 `/skills:project-engineering`。助手需要能够读取项目文件；要完成修改，还需要对应的文件写入和验证工具。

## 助手接下来应该做什么

它先读取目标路径适用的 `AGENTS.md`、贡献指南和相关文档。选择方案前，先检索活跃决策议题，读取相关提案、已选方案、否决理由和未决问题。重新讨论原有选择时，需要明确说明变化的条件。调查范围应随任务大小变化。只改一个组件，不应自动变成全项目审计。

设计过程中，它通过 `project-adr` 及时保存重要约束、真实否决理由和重大提案，暂不实施时也要保留有价值的进展。普通讨论和外部访谈技能复用同一议题记录。`project-adr` 负责记录内容和状态，`project-engineering` 按项目指令触发读取及同步。

随后，它沿着这次功能的调用关系找入口。如果项目已有统一导出服务，就确认是否适用于当前需求。如果客户端由 Schema 生成，就修改 Schema 并重新生成。一个文件使用某种写法，只能提供调查线索；要把它当作全项目规则，还需要更可靠的证据。

涉及持久化数据时，还要查清数据由谁负责、保存多久、怎样删除，以及派生缓存能否重建。纯页面按钮不必凭空增加数据库治理文档。

涉及生成物或持久数据变更时，助手会在修改前读取对应的[变更边界检查项](../../skills/engineering/project-engineering/references/CHANGE-BOUNDARIES.md)。主流程保留读取条件和完成检查，详细分支规则按任务需要加载。

实现后，助手运行与改动匹配的检查，查看实际结果，再核对文档和已有决策中的路径、默认值与实现是否仍一致。不能只写“已经验证”，却没有说明执行过什么。

## 最后会修改或生成哪些文件

没有每次调用都固定生成的文件。源代码路径由项目结构和任务决定。工程知识优先补进已有文档，下面几个路径是没有合适位置时的缺省选择。

| 文件或目录 | 什么时候会用到 | 保存什么 |
| --- | --- | --- |
| 目标模块、测试、必要生成物 | 实现任务需要修改时 | 实际功能和可执行验证 |
| `docs/engineering/ENGINEERING.md` | 有值得保留的工程发现，项目又没有合适的文档负责人 | 模块边界、复用条件、修改入口、验证限制 |
| `docs/engineering/DATA.md` | 本次涉及需要长期保留的数据规则，且没有现有负责人 | 数据所有权、生命周期、删除和重建约束 |
| 项目已有 ADR 目录 | 有长期价值的设计议题或实现变化需要记录时 | 提案、已选方案、否决理由、未决问题、证据和替代关系 |

例如，导出功能如果必须通过统一权限服务，这个约束以后还会影响其他导出入口，就值得保存。某个函数刚好在第几行，代码本身已经能查到，通常不需要再抄进工程文档。

目标项目没有决策规则时，`project-adr` 的默认目录是 `docs/adr/`。本集合自己的决策放在 `docs/agents/adr/`，这两个路径的适用对象不同。

## 怎样判断这次工作完成了

交付时应能看到实际 diff、已执行的检查及结果，以及知识文档的新增、更新或复用位置。没有值得长期保存的新发现，也可以不增加文件，但要说明原因。

检查 CSV 导出示例时，你需要确认字段和权限符合请求，相关测试覆盖了改动，生成物与源文件一致。打开助手提到的工程文档，应能找到有用的限制和依据，而不是一份复制代码目录的清单。

只要求只读调查时，结果应留在对话中，文件保持不变。commit、push 和发布 PR 需要各自的授权。需要专门处理理由、技术文字或提交时，可继续阅读[工程决策](project-adr.zh.md)、[技术写作](project-prose.zh.md)和[Git 操作](project-git.zh.md)。
