# Karpathy Guidelines 会怎样改变助手完成任务的方式

[English](karpathy-guidelines.md) | 简体中文 · [全部指南](../README.zh.md)

`karpathy-guidelines` 为现有任务增加一组工作原则。它要求助手先检查重要假设，采用足以解决问题的方案，把修改限制在请求范围内，再用实际检查支撑结论。交付时，读者应当知道完成了什么，以及证据到哪里为止。

本集合使用个人维护的改写版本，来源见[许可和出处说明](../../skills/thinking/karpathy-guidelines/NOTICE.md)。它参考 Andrej Karpathy 的观点，但不表示他编写或认可了这个集合。

## 什么时候值得明确调用

如果助手经常在修复一个问题时顺手重构其他模块，或者只说“已经修复”却不说明验证过程，就可以把这组原则放进任务。它同样适用于调研和写作，例如要求区分来源已支持的结论与仍待验证的推断。

它可以与具体工作流程一起使用。`project-engineering` 负责怎样进入项目、查找修改入口和保存工程知识，这组原则则贯穿整个任务，帮助控制范围和表达质量。

## 怎样交给助手

下面用一个重复保存问题作教学示例。

```text
$skills:karpathy-guidelines
修复重复点击保存后产生重复记录的问题。
先确认触发条件，再沿现有结构修改，不顺手重构其他模块。
用与修复匹配的检查验证结果，最后说明实际检查和未验证范围。
不要 commit 或 push。
```

示例使用本项目的 Codex 插件。单独安装时用 `$karpathy-guidelines`，Claude Code 中用 `/skills:karpathy-guidelines`。

## 工作过程会有哪些具体变化

助手应先查看现有实现和约束，确认“重复记录”究竟发生在页面、请求重试还是服务端。如果证据还不足，就保留这个不确定性，不把第一个猜测写成根因。

找到入口之后，改动应能够逐项对应你的请求。已有能力能够满足需求时，优先复用。确实需要一个辅助脚本或可视化来帮助验证，也可以创建，但应解释它解决哪个当前问题。

验证之后，报告要区分已执行的测试与仅从代码推断的行为。一个失败场景通过了，不能直接扩大成“所有并发情况都已解决”。

## 会不会生成固定文件

没有固定产物目录，也不会因为调用它就新增一份规范文件。

| 你原本的任务 | 可能得到的结果 |
| --- | --- |
| 修改代码 | 相关源文件和测试的改动，以及验证说明 |
| 调研问题 | 有来源支持的回答，以及仍缺证据的部分 |
| 修改文档 | 目标文档的更新和必要引用 |
| 需要图表或交互演示 | 与当前解释有关的可视化文件或展示，路径由任务决定 |

如果只要求在对话中解释概念，默认没有文件输出。它也不会替你自动创建 `AGENTS.md`、`CLAUDE.md` 或另一个个人 Skill。

## 怎样检查结果

从 diff 看，是否存在无法追溯到任务的改动。从报告看，是否说明了实际验证和限制。对于你关心的假设，应该能找到证据，或看到它仍被标为未知。

这些原则不能保证模型不犯错，也不能代替项目的测试、审查和授权规则。简单请求可以直接回答，不必为了显得认真强行插入长计划。详细内容见[执行指令](../../skills/thinking/karpathy-guidelines/SKILL.md)。
