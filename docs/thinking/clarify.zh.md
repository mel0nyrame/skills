# Clarify 怎样先问清一个会改变答案的问题

[English](clarify.md) | 简体中文 · [全部指南](../README.zh.md)

`clarify` 适合你已经提出一个想法，却还不确定自己最想解决什么问题的情况。希望先澄清意图或检验问题，再获得实质答案时，可以选择它。它会先检查问题里的假设，以及缺少哪些会影响答案的信息。如果仍有关键缺口，它只问一个最关键的问题。你回复后，它再给方案。

最初的意图检查只使用已有上下文，不调用工具，也不修改文件。助手专注于你要求的澄清，不同时开展无关工作。如果仍有会改变答案的信息缺口，助手只针对一个决定性维度提问一次，然后暂停。如果信息已经足够，助手会在同一轮直接回答，不额外声明信息充分，也不添加澄清栏目。

初始检查结束后，调查和执行遵循原始任务的授权。并非每个缺失事实都需要变成意图问题；目标已经明确的任务可能需要在授权范围内调查。助手会使用你的澄清回复继续原始任务。澄清回复本身不会扩大授权，也不要求你重新批准已经授权的动作。

## 哪种请求值得先澄清

“我想建个人知识库，推荐几个工具”包含很多尚未确定的条件。资料是否只给自己看，是否需要协作，眼下最难的是保存还是找回，都会改变推荐结果。直接给一串产品名称，未必解决了你当前的问题。

如果请求已经很明确，例如“把这个文件改名为 usage.md”，通常直接执行就足够。只有仍存在会改变答案的信息缺口时，`clarify` 才会增加一轮对话。信息充分时，助手会在同一轮回答，或继续已经授权的任务。

## 完整的一轮怎样进行

下面是一段教学示例，不代表已经替你测试过任何知识库产品。在安装本项目的 Codex 插件后发送。

```text
$skills:clarify
我想建立个人知识库，先帮我明确真正要解决的问题。
第一轮不要推荐产品，也不要修改文件。
```

需要澄清时，第一轮简短说明缺失条件，并提出一个决定后续方向的问题。仅在帮助你回答时补充假设或风险，无需固定输出多个栏目。最后的问题可能是下面这一类，实际问题由当前信息决定。

```text
你现在最想先解决哪一种困难，资料难以收集，还是已经保存却总找不到？
```

如果你的回答是“已经保存，但不知道当时为什么留它”，下一轮方案就应围绕保存上下文、整理主题和找回原始理由展开。它不应该继续给一份与回答无关的通用产品名单。

单独安装时用 `$clarify`，Claude Code 插件中用 `/skills:clarify`。上面的 `$skills:clarify` 是本集合 Codex 插件的名称。

## 会生成什么文件

| 阶段 | 你会看到什么 | 文件变化 |
| --- | --- | --- |
| 仍有关键缺口 | 简短说明与一个决定性问题，按需补充假设或风险 | 不调用工具，不改文件 |
| 信息已经足够 | 直接回答，不添加澄清框架 | 没有默认输出文件；后续动作遵循任务授权 |
| 你回答之后 | 针对原始目标的回答，或继续已经授权的工作 | 没有默认输出文件；原有任务授权仍然适用 |
| 初始检查后按授权调查或执行 | 原始任务要求的结果 | 仅在该授权范围内调用工具和修改文件 |

安装或调用 Skill 不会自动生成 `requirements.md` 或需求数据库。若你希望澄清后将需求保存到文件，可以在任务中指定 `docs/requirements.md` 等路径，同时说明只整理需求，还是继续实现。已有的保存或实现指令不需要在澄清后重复。

## 怎样判断它有没有帮上忙

看那个问题是否真的会改变后续答案。已经提供的信息不应重复询问，几个不同维度的问题也不应打包伪装成一个问题。回答之后，方案应该明确使用你的补充。

等待必要的澄清回复时，助手不应给出完整方案、启动浏览器或创建项目文件。信息充分时，助手应直接回答，不应编造缺口或误区。只有回复暴露出影响正确性或安全性的歧义时，才需要再问一轮。完整规则见[执行指令](../../skills/thinking/clarify/SKILL.md)。想直接约束整个任务的工作方式，可以看 [karpathy-guidelines](karpathy-guidelines.zh.md)。
