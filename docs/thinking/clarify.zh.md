# Clarify 怎样先问清一个会改变答案的问题

[English](clarify.md) | 简体中文 · [全部指南](../README.zh.md)

`clarify` 适合你已经提出一个想法，却还不确定自己最想解决什么问题的情况。希望先澄清意图或检验问题，再获得实质答案时，可以选择它。它会先拆出问题里的假设，指出缺少哪些会影响答案的信息，最后只问一个最关键的问题。你回复后，它再给方案。

它的第一项产物就是对话中的问题。第一阶段不调用工具，不创建文件，也不会先替你选好一套工具再补问需求。

## 哪种请求值得先澄清

“我想建个人知识库，推荐几个工具”包含很多尚未确定的条件。资料是否只给自己看，是否需要协作，眼下最难的是保存还是找回，都会改变推荐结果。直接给一串产品名称，未必解决了你当前的问题。

如果请求已经很明确，例如“把这个文件改名为 usage.md”，通常直接执行就足够。使用 `clarify` 会多出一轮对话，适合那些回答一个问题就能明显缩小范围的任务。

## 完整的一轮怎样进行

下面是一段教学示例，不代表已经替你测试过任何知识库产品。在安装本项目的 Codex 插件后发送。

```text
$skills:clarify
我想建立个人知识库，先帮我明确真正要解决的问题。
第一轮不要推荐产品，也不要修改文件。
```

第一轮应出现四部分内容，分别说明隐含假设、关键信息缺口、一个常见误区，以及一个决定后续方向的问题。最后的问题可能是下面这一类，实际问题由当前信息决定。

```text
你现在最想先解决哪一种困难，资料难以收集，还是已经保存却总找不到？
```

如果你的回答是“已经保存，但不知道当时为什么留它”，下一轮方案就应围绕保存上下文、整理主题和找回原始理由展开。它不应该继续给一份与回答无关的通用产品名单。

单独安装时用 `$clarify`，Claude Code 插件中用 `/skills:clarify`。上面的 `$skills:clarify` 是本集合 Codex 插件的名称。

## 会生成什么文件

| 阶段 | 你会看到什么 | 文件变化 |
| --- | --- | --- |
| 第一轮 | 假设、缺口、一个误区和一个问题 | 不调用工具，不改文件 |
| 你回答之后 | 针对原始目标的解释、建议或后续方案 | 没有默认输出文件 |
| 你另行要求保存答案 | 指定路径中的文档 | 在后续阶段按你的授权写入 |

安装 Skill 后也不会自动出现 `requirements.md` 或需求数据库。若你希望第二轮把确认后的需求保存到文件，可以明确要求写入 `docs/requirements.md`，同时说明暂时只整理需求，还是允许继续实现。

## 怎样判断它有没有帮上忙

看那个问题是否真的会改变后续答案。已经提供的信息不应重复询问，几个不同维度的问题也不应打包伪装成一个问题。回答之后，方案应该明确使用你的补充。

如果第一轮就给出完整方案、启动浏览器或创建项目文件，就没有遵守这个 Skill 的两阶段流程。只有回复暴露出影响正确性或安全性的歧义时，才需要再问一轮。完整规则见[执行指令](../../skills/thinking/clarify/SKILL.md)。想直接约束整个任务的工作方式，可以看 [karpathy-guidelines](karpathy-guidelines.zh.md)。
